# Session Report

## What This Session Was About

Investigating a crash in the `codegraph init -i` command, which failed with a fatal Node.js out-of-memory error ("Fatal process out of memory: Zone") while indexing a large TypeScript project. The environment is WSL2 on Windows 11.

## What Was Handled

**Root cause investigation.** The crash was traced to a V8 internal memory allocator failure, not ordinary JavaScript heap exhaustion. The indexing tool runs on its own bundled Node runtime and parses files using WebAssembly-based tree-sitter grammars.

**Key findings from the investigation:**
- The tool indexes files through a single worker thread that parses with WebAssembly grammars.
- WebAssembly memory can grow but never shrink, so the tool periodically recycles the worker to reclaim memory.
- The specific crash type is a native abort that cannot be caught by the tool's own error handling, so its recovery logic never gets a chance to run.
- The crash occurred after roughly 500 files were indexed, which aligns with the worker-recycle boundary.
- The default memory ceiling for the bundled runtime is about 4.2 GB, and the worker plus WebAssembly memory can push the process past that limit.

**The fix.** Raising the memory ceiling for the bundled runtime via the `NODE_OPTIONS` environment variable. This was verified to propagate correctly through the tool's launcher.

**Scoping the fix.** Rather than applying the memory setting globally (which would affect every Node process on the system), a shell function was added so only the codegraph command gets the larger memory ceiling. The function was added to the user's shell aliases file.

**MCP server configuration.** The codegraph MCP server (which runs `codegraph serve`) was configured to inherit the same memory setting, since it is launched directly and would not pick up the shell function. The environment variable was added to the MCP server configuration in the Claude settings file.

## Important Choices

- **Scoped the memory fix** to only the codegraph command instead of exporting it globally, to avoid masking memory issues in other Node processes and to prevent a runaway process from consuming up to 8 GB of system memory.
- **Used a shell function wrapper** so the memory setting applies only when codegraph is invoked, keeping the rest of the system on default settings.
- **Configured the MCP server separately** with the environment variable, since MCP servers are spawned directly and do not load the user's shell configuration.

## Current State

- The root cause is identified: a V8 internal memory allocator failure during WebAssembly-based parsing, triggered when the indexing process exceeds its default memory ceiling.
- A fix is in place via a shell function that gives codegraph a larger memory ceiling.
- The MCP server configuration has been updated to include the same memory setting.
- The partial index (about 500 files) is valid and the indexing can resume from where it stopped.

## What Still Needs Attention

- The currently running MCP server process will not pick up the new configuration; it needs to be restarted for the change to take effect.
- The fix has not yet been verified end-to-end by running the full indexing to completion.
- The shell function only takes effect in new shells (or after sourcing the aliases file), so any already-open terminal will not have it.

## Suggested Next Steps

- Run `codegraph init -i` again with the fix in place to confirm the full indexing completes without crashing.
- Restart the MCP server so it picks up the new environment variable.
- If the crash persists even with the raised ceiling, consider whether the tool has a known issue with large repositories and check for a newer version or a configuration option to reduce worker memory usage.
